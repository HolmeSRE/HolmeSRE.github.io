HolmeSRE: Demystifying Scheduling Failures in Hyperscale Clusters with an Agentic Troubleshooter

The ideal reasoner would, when he had once been shown a single fact in all its bearings, deduce from it not only all the chain of events which led up to it but also all the results which would follow from it. — Arthur Conan Doyle, The Five Orange Pips

A 4B agent that troubleshoots like an SRE. HolmeSRE retrieves scheduling context, establishes local facts with deterministic checks, and correlates them into a root cause. On real production failures it matches 2.4T flagship models while answering in seconds.

Abstract

Hyperscale ML clusters increasingly encounter scheduling failures, where task placement becomes infeasible under coupled resource availability and scheduling policies, leading to prolonged queueing and substantial operator toil. We study 169 confirmed failure reports from Aug.–Dec. 2025 in Platform-X, a production MLaaS platform at Alibaba Group managing 6,700+ heterogeneous GPUs. Our analysis shows that scheduling-policy induced infeasibility is the most prevalent failure category and that diagnosis requires correlating heterogeneous, large-scale context artifacts, with frequent recurrence exacerbating the operational burden. Current practice remains manual and difficult to scale. Motivated by these findings, we propose HolmeSRE, an automated troubleshooter that iteratively retrieves context, establishes local facts via deterministic checks, and correlates them to identify root causes. HolmeSRE controls tool interaction via action abstraction, learns procedural investigation from synthesized trajectories, and aligns intermediate steps with a diagnostic topology. On 332 held-out real failures, HolmeSRE-4B, trained only on synthesized failures, achieves 92.88% Macro-F1, on par with 2.4T flagship models at 16× lower latency. In a one-month production deployment, SREs assisted by HolmeSRE identified all root causes while troubleshooting 5.8× faster.

01 MOTIVATION

Why are scheduling failures hard to troubleshoot?

At hyperscale, a placement can be infeasible while GPUs sit idle. Finding out why means searching coupled constraints across massive, heterogeneous context.

Task formulation
𝒪=ℱ(ℛ,𝒮,𝒫)

The scheduler deterministically maps a workload specification, the cluster state and scheduling-policy constraints to a placement 𝒪. A scheduling failure is 𝒪 = ⊥.

Diagnosis localizes a minimal subset 𝒞 ⊆ ℛ ∪ 𝒮 ∪ 𝒫 whose joint constraints make the placement impossible, e.g. a workload constraint that conflicts with a policy under the current state.

Logical complexity

Schedulability emerges from interacting resource and policy constraints whose dependencies and evolution make root-cause attribution hard.

Data complexity

The decision context of one event is spread across large volumes of specifications, cluster states and policy configurations.

04 FROM FINDINGS TO DESIGN

Three challenges for troubleshooting automation

Scheduling failure diagnosis is an admission-time, constraint-based task, so it is amenable to verifiable, tool-mediated procedures over captured context. The findings expose what such automation must handle.

Challenge 1

Explosion of the diagnostic search space

Over 10 million characters nested about 15 levels deep; root causes are dispersed across nearly 270,000 leaf nodes.

From Finding 3
HolmeSRE · Action abstraction

Keep raw payloads out of the context window

Retrieve fetches artifacts but returns only compact logical keys. Raw JSON is handled by tools, so the agent’s context stays small and controllable.

Challenge 2

Complexity of cross-domain correlation

Root causes arise from coupled conditions across workload specs, quotas, cluster states and federation policies.

From Findings 1–3
HolmeSRE · Deterministic checks + topology

Verify local facts, then correlate them

Diagnosis runs SRE check code and returns local facts. The agent decides which facts to establish, following the diagnostic topology from intent to resources to policy.

Challenge 3

Operational scalability and redundancy

Queueing averages 40.71 minutes, nearly 3× the hands-on time, and 66% of failures recur with known root causes.

From Finding 4
HolmeSRE · Learned procedure

A compact agent that answers in seconds

A 4B model learns the troubleshooting procedure from synthesized expert trajectories and serves every reported event, so SREs review instead of queueing.

05 METHOD

How does HolmeSRE troubleshoot?

Two abstract actions, a procedure distilled from synthesized expert trajectories, and preferences that keep intermediate steps consistent with the diagnostic topology.

Retrieve

Logical Context Mechanism

Fetches the underlying artifact, such as a full cluster-state snapshot, but returns only a compact set of structured logical keys that reference relevant fields. Verbose JSON is deferred until a check needs it.

Inputretrieve(data=["pod_spec"], pod_uid="pod_abcd1234")
Output{"logical_keys": ["pod/spec"]}
Diagnosis

Deterministic SRE checks

Given logical keys and a natural-language instruction, runs the check code SREs routinely use, e.g. comparing remaining quota with the request or computing the largest free GPU block, and returns a local fact, never a verdict.

Inputdiagnosis(keys=["pod/spec"], instruction="Check whether the pod specification is valid.")
Output"Pod configuration is valid"

A local fact alone rarely determines the root cause: “no node can host the instance” is consistent with fragmentation, excessive reservation or global insufficiency. The agent decides which facts to establish and infers the root cause from their joint evidence.

Topology-Modulated DPO

Standard DPO penalizes every dispreferred trajectory equally. Treating outcome-correct but topology-invalid trajectories as hard negatives can erase accuracy learned from imitation. TM-DPO rescales each pair by a topology-dependent coefficient λi.

At zero margin, the gradient is 0.50× that of standard DPO.

10 LESSONS LEARNED

What we would tell the next team

Practical lessons for building reliable troubleshooting automation in hyperscale AI infrastructure.

01

Diagnose constraints, not capacity

Scheduling Policy Blockage (45.6%) outnumbers resource shortfalls (33.1%), as isolation-driven constraints render healthy capacity logically unreachable. Audit scheduling constraints before adding capacity.

02

Design the interface before scaling the model

With over 10 million characters of context per event, raw artifacts overwhelm any model. In a generic coding agent the same model falls from 90.96% to 22.01%, while a 4B model with task-specific actions rivals 2.4T flagships.

03

Learn the procedure, not just the answer

By imitating expert trajectories, a compact 4B model learns troubleshooting from synthesized failures alone and applies it to real ones. Outcome-only supervision still rewards right answers with wrong reasons, so topology preferences keep intermediate reasoning valid.

04

Verifiability drives adoption

Autonomous diagnosis struggles with complex resource and constraint failures, but SREs reviewing explicit trajectories reach 100% accuracy 5.8× faster. A verifiable assistant beats an opaque one, provided failure synthesis keeps pace with evolving policies.

11 CONCLUSION

Conclusion

Scheduling failure diagnosis is hard not because resources are scarce, but because schedulability is shaped by coupled policy constraints, massive heterogeneous context, and recurring failures that overwhelm manual troubleshooting. HolmeSRE answers with iterative evidence retrieval, deterministic verification, a learned troubleshooting procedure, and topology-aligned reasoning.
